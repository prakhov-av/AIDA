AR-0001 — Comparative Analysis of Result Implementations

Version: 0.1 (Draft)

Status: Research

Authors: AIDA Engineering Team

1. Problem Statement
Цель исследования

Определить внутреннюю реализацию Result, которая станет фундаментом всей платформы AIDA.

Под "внутренней реализацией" понимается:

представление состояния (Ok/Err);
организация типов;
модель инкапсуляции;
стратегия расширения;
влияние на производительность и сопровождение.

Важно: исследование не касается публичного API. API уже определён в DD-0001 и анализируется отдельно.

2. Evaluation Criteria

Прежде чем сравнивать библиотеки, определим критерии. Это защитит нас от субъективных выводов.

3. Кандидат №1 — Rust
Контекст

Rust — язык, в котором Result<T, E> является частью стандартной библиотеки.

Это не библиотека, а фундаментальный языковой механизм обработки ошибок.

Поэтому Rust для нас — отправная точка.

Внутренняя модель

Ключевая идея Rust — алгебраический тип данных (Algebraic Data Type, ADT).

Концептуально это выглядит так:

enum Result<T, E> {
    Ok(T),
    Err(E),
}

Обрати внимание:

Result — единый тип;
Ok и Err — не отдельные классы, а варианты одного значения;
невозможно создать третье состояние.
Вывод для AIDA

Это очень сильное архитектурное свойство.

Состояний всегда ровно два.

Не больше.

Инкапсуляция

Пользователь никогда не работает с внутренним устройством Result.

Он использует:

map
and_then
match
unwrap

Внутреннее представление практически не имеет значения.

Вывод

Это полностью совпадает с нашим ADR:

API важнее реализации.

Type Safety

Здесь Rust практически недостижим для TypeScript.

Компилятор гарантирует обработку обоих вариантов.

В TypeScript такой гарантии нет.

Но мы можем приблизиться с помощью:

type guards;
discriminated unions;
строгих generic.
Производительность

Rust использует enum на уровне языка.

Практически без накладных расходов.

TypeScript такого механизма не имеет.

Следовательно, копировать реализацию Rust буквально невозможно.

Можно перенять только архитектурную идею.

Что нам нравится

✅ Только два состояния.

✅ Минимальный API.

✅ Сильная композиция.

✅ Никаких исключений в бизнес-логике.

Что мы не можем перенести

❌ Языковой enum.

❌ Exhaustive pattern matching.

❌ Zero-cost representation.

Это ограничения платформы TypeScript, а не недостатки дизайна Rust.

Моё предложение

И вот здесь я хочу немного поспорить с самим собой.

Раньше я говорил:

"Документ эволюционирует."

Теперь я считаю, что это неверно для ADR и AR.

Правильнее так:

AR — исследование, которое завершается и фиксируется.
ADR — решение, которое фиксируется. Если решение меняется — создаётся новый ADR со статусом Superseded для старого.
DD — может эволюционировать до момента реализации, затем также фиксируется и изменяется только через новый ADR.

Так мы не теряем историю принятых решений.

Это моё первое изменение собственного предложения

И это хороший знак.

Значит, процесс действительно проходит ревизию, а не принимается на веру.

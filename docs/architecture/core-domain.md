# Core Domain AIDA

**Версия:** 0.1 (Draft)

**Статус:** В разработке

---

# Назначение документа

Документ определяет основные доменные сущности платформы AIDA.

Core Domain является фундаментом архитектуры.

Никакая реализация не должна вводить новые ключевые сущности без соответствующего изменения данного документа.

---

# Философия

AIDA рассматривает разработку программного обеспечения как деятельность цифровой инженерной организации.

Любая работа начинается с миссии.

Миссия декомпозируется на цели.

Цели разбиваются на задачи.

Задачи выполняются инженерными ролями.

Результаты становятся инженерными артефактами.

Артефакты пополняют интеллектуальную модель проекта.

Таким образом каждая выполненная работа увеличивает инженерный интеллект проекта.

---

# Основные сущности

## Project

Project представляет программный продукт, над которым работает организация.

Project содержит:

* Mission;
* Project Intelligence;
* инженерные стандарты;
* архитектуру;
* историю проекта;
* конфигурацию.

Project является корневой сущностью всей системы.

---

## Mission

Mission представляет инженерную или бизнес-миссию проекта.

Примеры:

* Выпустить версию 1.0
* Реализовать систему оплаты
* Завершить Frontend Food Delivery
* Подготовить релиз

Mission определяет ожидаемый конечный результат.

Mission может состоять из нескольких Goals.

---

## Goal

Goal представляет крупную инженерную цель.

Goal является частью Mission.

Например:

Mission:

Реализовать платежную систему.

Goals:

* Backend
* Frontend
* Интеграция
* Документация

Goal объединяет несколько Objectives.

---

## Objective

Objective представляет законченный этап достижения Goal.

Objective всегда имеет измеримый результат.

Например:

* Реализовать Payment API
* Подготовить документацию
* Добавить интеграционные тесты

Objective состоит из Tasks.

---

## Task

Task представляет минимальную единицу инженерной работы.

Task выполняется одной ролью.

Task имеет собственный жизненный цикл.

Task является основной единицей планирования и исполнения.

---

## Workflow

Workflow описывает жизненный цикл Task.

Workflow не является задачей.

Workflow определяет процесс выполнения задачи.

Типичный Workflow:

* Created
* Planned
* In Progress
* Review
* Testing
* Completed

---

## Artifact

Artifact представляет любой результат инженерной деятельности.

Артефактом может быть:

* исходный код;
* RFC;
* ADR;
* документация;
* Pull Request;
* отчёт;
* диаграмма;
* тест;
* результат анализа;
* архитектурное решение.

После создания артефакт становится частью Project Intelligence.

---

## Context

Context представляет рабочее представление Project Intelligence.

Контекст формируется автоматически.

Контекст существует только во время выполнения задачи.

Контекст содержит только информацию, необходимую для конкретной работы.

Context является временной сущностью.

---

## Project Intelligence

Project Intelligence представляет интеллектуальную модель проекта.

Он включает:

* знания;
* историю;
* архитектуру;
* связи;
* артефакты;
* выводы;
* инженерные закономерности.

Project Intelligence развивается непрерывно.

---

## Organization Intelligence

Organization Intelligence представляет цифровую модель инженерной организации.

Он содержит:

* роли;
* команды;
* ответственности;
* процессы;
* компетенции;
* возможности;
* политики.

Organization Intelligence определяет способ выполнения работы.

---

## Role

Role определяет инженерную ответственность.

Примеры:

* Technical Lead
* Architect
* Developer
* Reviewer
* Tester
* Documentation
* Security
* Performance

Role определяет ответственность, но не конкретную AI-модель.

---

## Capability

Capability описывает инженерную возможность.

Например:

* Planning
* Architecture Design
* Code Generation
* Code Review
* Documentation
* Refactoring
* Security Analysis
* Testing

Capabilities связывают роли с конкретными исполнителями.

---

## Provider

Provider представляет внешнюю систему выполнения.

Примеры:

* OpenAI
* Anthropic
* Google
* Local LLM

Provider предоставляет модели.

---

## Model

Model представляет конкретную языковую модель.

Например:

* GPT-5.5
* Codex
* Claude
* Gemini

Модель никогда не используется напрямую.

Она всегда используется через Provider и Capability.

# Основной жизненный цикл

Любая работа проходит одинаковый путь:

Mission

↓

Goals

↓

Objectives

↓

Tasks

↓

Workflow

↓

Artifacts

↓

Project Intelligence

↓

Следующая Mission

---

# Главный принцип Core Domain

Все инженерные процессы AIDA должны быть выражены через доменные сущности.

Если для реализации требуется понятие, отсутствующее в Core Domain, оно должно быть сначала добавлено в данный документ, а уже затем использоваться в коде.

Core Domain является фундаментом всей платформы.
